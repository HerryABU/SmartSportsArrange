## 1. 检索到的四篇核心工作

### 1.1 可采纳的神经启发式 — arXiv:2606.04860（2026-06）

**核心结论**

- A\* 类算法保持**最优性**的前提是启发函数**可采纳**（never overestimate 真实剩余代价）；
- 用 MSE 训练代价网络会**系统性地高估**，从而破坏可采纳性、**剪掉本不该剪的分支**；
- 修法三件套：**① 可采纳 Bellman 算子（低估）** + **② 非对称损失（对高估加重惩罚）**
  + **③ 验证集上的事后校准安全偏移**；
- 效果：2×2 魔方节点扩展 −83%，无一次可采纳性违例。

**对我们的意义**

`days_estimate` 与 `quality_score` 正是**MSE 训练的代价型输出**。
此前我们把它们当"参考"，但如果**拿它们剪枝**，高估会以
「莫名其妙剪掉了可行解」的形式出现，而且**不报错**——这是最难查的一类。

**已落地**（`sports_ai/plan/hybrid_search.py`）

| 论文要素 | 我们的实现 |
|---|---|
| 低估取向 | `CompletionPredictor.w_over = 4.0 > w_under = 1.0`（对「预测能完成、实际不能」重罚） |
| 校准偏移 | `CompletionPredictor.calibrate(feats, labels, quantile=1.0)` → 取最大高估量作 `calib_delta` |
| 可采纳性判据 | `is_admissible(estimate, true_cost)`，并由单测逐样本断言校准后无违例 |
| **只排序不剪枝** | `plan_predictive` 里预测值只进 `score()` 排序；可行性由 `verify_slot_map` **确定性裁决** |

> 这最后一条是我们比论文更保守的地方：论文用可采纳启发式**指导剪枝**，
> 我们进一步规定**预测永不参与剪枝判决** —— 多花一点搜索，换「不可能因为预测错而丢解」。

### 1.2 回溯搜索中的验证器 — arXiv:2605.22221（2026-05）

**核心结论**

用**累积轨迹**做自回归训练的解码器，在「继续 or 回溯」判定上有两个失败模式：

- **scattered retrieval**：状态特征散落在序列的多个位置，模型难以取用；
- **history entanglement**：预测器条件于**轨迹**而非**状态** —— 两条到达同一状态的不同轨迹会给出**不同**判定。

修法：**localization**（重写决策块让状态特征局部化）+ **Selective State Attention**
（固定注意力掩码，结构化强制「基于状态」决策，不改数据/目标/参数）。
另给出**免重训方案**：推理时清空上下文。

**对我们的意义**

我们的「预测下一步能不能走通」如果直接吃落位轨迹，会踩同样的坑。

**已落地**

采用论文的**免重训那条路**（推理时隔离），但做得更彻底：**从接口上就不给历史**。

```python
# StateView.feat() 只含「从当前状态可算」的量：
#   填充率 / 容量余量 / 剩余兼项暴露 / 块断裂度 / 工期占预算比 /
#   剩余未排比例 / 负载离散度 / 当前是否仍可能可行
```

单测 `test_state_features_depend_only_on_state_not_history` 直接钉住
「同一状态 → 逐位相同特征」。这是**结构性隔离**，不依赖注意力掩码，也不需要重训。

### 1.3 搜索-失败-恢复的训练框架 — arXiv:2607.07492（2026-07，Pyligent）

**核心结论**

把推理视为**经过验证的搜索**：验证器标记生成的延续与失败，
把搜索树转成三种动作的监督目标 —— **继续 / 完成 / 回溯**，并可选给出放弃分支的总结。
相比只模仿成功路径的监督微调，在隐藏图上解决率 **+72.7 个百分点**。

**对我们的意义**

直接给出「回退」应有的**标签结构**：**失败分支同样是监督信号**。

**已落地**

| 论文要素 | 我们的实现 |
|---|---|
| 三动作 | `SearchLog.continues / completes / backtracks`，外加 `repairs / restarts / rollbacks` |
| 回溯原因可诊断 | `SearchLog.backtrack_reasons`（无候选 / 完成校验失败 / 触达上限） |
| 失败分支也是监督信号 | `collect_training_pairs()` 用 DFS 跑**验证搜索树**，把每个状态的「最终能否完成」当标签（含大量 0） |

单测 `test_collect_training_pairs_marks_infeasible_states` 断言标签里**必须出现 0** ——
如果只会收集成功样本，这条会失败。

### 1.4 双层优化与 3R 恢复 — arXiv:2606.06877（2026-06）

**核心结论**

把神经打分器放**上层**、把符号规划放**下层**（在下层于上层打分剪枝后的空间里求解），
会带来 **exposure bias**（训练在全空间、部署在自剪枝空间）。
修法是在下层引入 **3R：Repair / Restart / Rollback** 提供可靠反馈。
结果：失败率 **−80%**，规划时间 **−57%**。

**对我们的意义**

这正是「模型当种子 + 算法精修」的**严格形式化**。我们已有全部三个 R，但此前**没有统一定义**。

**已落地**

| R | 我们的对应 | 触发条件 |
|---|---|---|
| **Repair** | `solve/repair.py` + `plan/_try_repair` | 方案局部不可行（容量超载 / 兼项撞车）；**只修「能不能」，不修「好不好」** |
| **Restart** | GA 多起点重启 + `plan_predictive(max_restarts=…)` | 连续无改进 / 整趟失败；**换序时保留启发式信息**（不纯随机） |
| **Rollback** | 决策点回退（`dfs` 里撤销最近一次落位并穷举其余候选） | 该子树被判定无解 |

三个 R 的顺序是 **先 Repair、再 Rollback、最后 Restart** —— 越便宜的越先试。
单测里专门构造了「Repair 修不动 → 必须 Rollback」的场景（`b` 只有一个候选槽），
以及「首趟必败 → Restart 计数增加」的场景。

## 3. 已实现的架构升级：启发式 + 搜索网络 + 预测网络（可回退）

新模块 `sports_ai/plan/`（`hybrid_search.py`），把用户要的三件事组装成一条链：

```
启发式序（MSBF 紧度：候选越少越先排 —— 确定性，不依赖模型）
   │
   ├─ 搜索神经网络：neural_prior(unit, slot)   ── 只用模型的 slot_logits 排序候选
   ├─ 预测网络：CompletionPredictor(state)     ── 只判断「当前状态能否排完」
   │
   ▼
候选按 score = neural_prior + 0.5×predictor(state) 排序
   │  ⚠️ 预测值经 conservative_value 保守化（低估 + 校准偏移）
   ▼
逐单元落位 → 校验器裁决（容量 / 兼项 / 场地是否开）
   │  不通过 → ① Repair（换槽）→ ② Rollback（回溯）→ ③ Restart（换序）
   ▼
PlanResult{ slot_of, feasible, violations, blocked, log, value }
```

### 3.1 关键设计决策

| 决策 | 理由 |
|---|---|
| 启发式序**不依赖模型** | 模型缺失 / 旧版 onnx 时仍能工作；模型只用来**改进顺序**，不决定可行性 |
| 预测值**只排序、不剪枝** | 唯一能保证「预测错了也不会丢解」的做法（`verify_slot_map` 独占裁决权） |
| 校验器**把「场地未开」判不可行** | 早期把 `caps` 缺失当「容量无限」，会让方案看起来可行、实际排不进去 |
| Repair 优先于 Rollback | 换槽的成本远低于整条路径回退（与论文的 3R 顺序一致） |
| Restart **保留启发式信息** | 纯随机重启会丢掉「紧的单元先排」这个下界信息，等于从零开始 |
| 状态特征**只含当前状态** | 结构性避免 history entanglement，不依赖注意力改造与重训 |
| 失败分支**也进训练集** | 只学成功路径的模型学不会「何时该回退」 |

### 3.2 实测（真实场景，seed=7）

用生成器的五档真实场景（槽 = 时间桶；容量键 = (槽, 场地)）跑 `plan_predictive`：

| 档 | 单元数 | 槽数 | 可行 | 未排 | 回退 | 修复 | 重启 | 耗时 |
|---|---|---|---|---|---|---|---|---|
| HELL（魔鬼） | 53 | 15 | ✗ | **5** | 97 | 3 | 2 | 0.06s |
| REGULAR | 49 | 9 | ✗ | **1** | 24 | 3 | 2 | 0.03s |
| BLOCK | 77 | 12 | **✓** | **0** | 21 | 0 | 0 | 0.03s |
| LANE | 34 | 8 | **✓** | **0** | 5 | 0 | 0 | 0.03s |
| TEAM | 35 | 12 | **✓** | **0** | 0 | 0 | 0 | 0.03s |

**三档完全解出**（BLOCK / LANE / TEAM，未排 0），HELL 与 REGULAR 剩少量未排 ——
并且**零容量/兼项违规**（`violations` 里只剩「未排」，没有任何非法落位）。

**为什么 HELL 排不完是「诚实」而不是「失败」**：把那几个单元逐个查过，
它们的场地容量已被前序单元占满（区间求和恰好卡死），让位链加深到 8 层也无法腾出空间。
继续加深只会空转到回退上限（depth=8 时回退 20027 次、耗时 5.4s 仍未改善）。
此时**如实报「未排 5」比返回一个超容方案有用得多** —— 后者在现场意味着"赛程打出来但排不进去"。

⚠️ **口径提醒**：上表的「未排」是**本模块自洽口径**（每 (槽, 场地) 的分钟容量求和），
与 `benchmarks.md` 里 GA/模型链路的「未排」不是同一套解码口径，**不可直接跨表比较**。
这里要说明的是**规划层本身能工作**，而不是「超过了 GA」。

### 3.3 预测器实测（可采纳性保护生效）

以 LANE 场景跑 `collect_training_pairs` 收标签（蒙特卡洛式验证搜索树）：

```
状态样本 69 个，标签分布 [53 个"不可完成", 16 个"可完成"]
欠训（1 epoch）时：loss=0.836，高估样本数 > 0        ← 目标态"乐观"确实存在
校准（quantile=1.0）：delta = 0.4069
校准后：可采纳性违例 = 0 / 69                        ← 与 arXiv:2606.04860 的结论一致
```

这正好复现了论文的因果链：**MSE 训练 → 乐观 → 校准偏移 → 零违例**。
只有走到这一步，预测值才敢参与「先试哪条分支」的排序。

### 3.4 开发过程中修掉的三个真问题

写这个原型时暴露出的都不是"新功能缺失"，而是**既有数据的结构性问题**：

| 问题 | 症状 | 修法 |
|---|---|---|
| **影子任务窗口容量写死** | `add_shadow_tasks` 给裁判/教师单元的 V0 窗口容量写死 `max(120, w0.capacity//2)`，而它们实际需求常达 200+ 分钟 → **客观装不下**；此前靠 `greedy_targets` 的「放不下就退到最大桶」兜住，但那产出的是**超容标签**：模型学到「超容也算排下了」，而确定性校验器会判它不可行 —— 训练与部署的可行性口径分叉 | 容量按影子任务**实际需求 ×1.2** 分配 |
| **影子单元随机共享运动员 ID** | 裁判组用 `rng.randint(1000,1011)` 取 ID，两个裁判组可能撞同一个 ID；而所有影子单元又被强制进**同一个 V0 槽** → 「同槽同人」让它们**永远排不下**（每次固定 2~3 个钉子户） | 改为按序号取唯一 ID（它们本来就是不同的裁判组/教师） |
| **搜索的"排序"与"剪枝"混淆** | 早期只在**候选排序**里给兼项冲突打 `-inf`，没有在落子时剪枝 → 搜索反复生成「同槽同人」的**完整方案**、校验失败、修复也修不动、回退后又走同一条确定性路径 —— 实测空转到 2 万次回退，**一个单元都没排下** | 把兼项提到 `_local_ok`（前向检查）；并且 ejection 让位后**必须重做一次前向检查**才能提交（第一版直接塞进去，引入了"超容 180>179"与"兼项撞 REF0/REF2"却对外报 blocked=[]） |

> 最后一条是最值得记的：**「只排序」和「只剪枝」都是错的**。
> 正确的分工是 —— **可行性判定（剪枝）必须确定性且尽早**；
> **模型与预测只影响顺序**。混在一起就会出现「看起来排下了，其实方案非法」。

### 3.5 可诊断输出

`PlanResult.log` 明确区分六个计数，用于回答「这次到底回退了几次、为什么」：

```json
{"continues": 37, "completes": 1, "backtracks": 3, "repairs": 2,
 "restarts": 1, "rollbacks": 3,
 "reasons": ["完成校验失败:兼项撞:7@0(a,b)", "无候选:REF2"]}
```

> 这一条本身就是对旧设计的改进：**原来「方案没排好」只有一个结果，没有过程**。
> 现在能回答「是容量不够、兼项互斥，还是候选集本身为空」。

## 4. 已完成：把预测器接进正式评测（同预算协议）

§4 原来的 TODO 已全部落地，并且**实测结论与原预期不完全一致** —— 下面如实记录。

### 4.1 对比协议：为什么不能用「解逐位一致」

最初的设想是「同解质量下节点扩展数更少」。落到本问题上发现**不可实现**：

> 贪心是「按确定性候选序试，**首个通过前向检查的槽即选中**」。
> 学习式剪枝一旦跳过某个候选，而它恰好是首个可行槽，就会改选后面的 ——
> **决策变了，解必然不同**。所以「省扩展」与「解完全一致」不可兼得。

于是改用**同扩展预算比解质量**：两侧都跑满同一节点扩展预算，
预测器每次尝试更省 → 同样预算能跑更多次重启。这是可实现且可比的替代口径。

### 4.2 实测（真实五档场景，2 seeds 均值，扩展预算 4000）

| 档 | 扩展数（无/带） | 节省 | 剪枝 | 重启（无/带） | 代价（无/带） | 守卫代价 | 守卫不劣 |
|---|---|---|---|---|---|---|---|
| HELL | 4492 / 4044 | 9.8% | 5511 | 10 / **42** | 134.5 / 139.0 | **134.5** | ✅ |
| REGULAR | 4201 / 3754 | 10.3% | 7626 | 10 / **54** | 29.0 / 29.5 | **29.0** | ✅ |
| BLOCK | 4080 / 4066 | 0.3% | 9102 | 14 / **43** | 104.0 / 104.0 | 104.0 | ✅ |
| LANE | 2118 / 2146 | **−0.7%** | 1376 | 13 / 17 | 19.5 / 19.5 | 19.5 | ✅ |
| TEAM | 4032 / 2545 | **36.9%** | 5063 | 16 / **59** | 31.5 / 31.5 | 31.5 | ✅ |
| **合计** | **18923 / 16555** | **12.5%** | — | — | — | — | — |

> **守卫式组合的价钱**：两个解都要算，所以扩展数是两者之和 ——
> 合计 **18923 → 35478（+87.5%）**。这是「解质量单调不劣」这个结构保证的价格，
> 必须如实报出来。选择口径：
> * **要确定性**（生产默认）→ 用守卫式组合，代价是约 1.9× 扩展；
> * **搜索预算是瓶颈**（离线、大规模压测）→ 用纯剪枝，接受偶发的解扰动。

⚠️ **LANE 出现 −0.7%**（带预测反而多花 28 次扩展）。原因不是 bug：
该档实例很松（未排 1.0，容量余 1736），确定性启发**第一次就选中了可行槽**，
根本没有「注定失败的候选」可剪；而剪枝本身要调预测网络（1376 次），
这些调用以及被剪后重试的候选，反而比基线多做了几次检查。
**结论：实例越松，学习式剪枝越无收益甚至微亏 —— 它只在紧实例上有用。**

**三条必须说清楚的结论：**

1. **单次尝试的节省很大（65~89%，不受预算约束时测），但换算成同预算后总节省缩小到 0~37%**
   （合计 12.5%）。原因很直白：省下的扩展被用来跑更多次重启（HELL 10→42、TEAM 16→59），
   总消耗自然回升。**「省了多少」取决于你把预算花在哪** —— 只报单次节省是误导。
2. **纯剪枝会扰动解，在 HELL/REGULAR 上反而略差**（134.5→139.0 / 29.0→29.5）。
   这正是上面那条「决策必然改变」的直接后果。所以生产口径必须是
   **守卫式组合**：最终解 = min{基线解, 预测器解} —— 于是「解质量单调不劣」
   是**结构保证**，不依赖预测器准不准。上表最后一列五档全 ✅。
   代价是要跑两遍，扩展数相加；这个开销已作为 `guarded_overhead_pct` 如实报出。
3. **重启没能提升解质量**（基线从 10 次重启加到 42 次，代价仍是 134.5）。
   说明当前的重启算子（顺序旋转 + 偶次打散）**不产生有效多样化** ——
   贪心很快就回到同一个局部最优。所以「省下的预算换质量」这条路目前走不通；
   下一个真正的杠杆是**换更强的多样化算子**（如按「关键单元」重排、
   或对已排方案做破坏-重建），而不是继续省扩展。这条已写进 §5 的下一步。

### 4.3 ⚠️ 途中挖出的一个真缺陷：预算耗尽被当成「不可行」

第一版标签生成是「穷举 DFS，每个状态标『子树里有没有成功叶子』」，两个致命问题：

| 问题 | 症状 | 修法 |
|---|---|---|
| **预算耗尽误标为不可行** | `if len(feats) >= max_states: return False` 的 `False` **沿递归上传**，把整条祖先链标成「排不完」。实测 HELL 采到 1182 个样本，**标签 100% 是 0** | 区分「未知」（返回 `None`，且祖先保持未知）与「确定不可行」；最后**只保留确定样本** |
| **穷举在真实规模上不可达** | 分支是 `∏|cands|`，18 单元 × 4 候选 = 4¹⁸；DFS 只到第 5 层就吃光预算，**从未到达 `depth == n`**，一个成功叶子都产生不了 —— 这正是上一条被触发的原因 | 改为 **rollout 标签**：沿真实规划路径落位，每步问「贪心补全从该状态能否排完」，成本**线性** |

**后果有多严重**：标签全 0 → 预测器输出退化成常数 0.0033（零区分力）→
规划层里 `s += 0.3 * 常数` 只是**固定偏移**，对候选排序毫无影响
→ 消融显示「带预测 vs 不带预测」的扩展数**完全相同**（4581 / 4581，节省 0.0%）。

> 教训：**「预算用尽」不是「结论为否」**。任何「搜索到一半停下」的地方
> 都必须把「未知」与「否」分开，否则会把「没查完」当成「查过了，不行」。

### 4.4 预测器现在的正确用法（保守剪枝 + 三道保险）

`plan_predictive` 新增 `pred_prune_below`（默认 0.15）与 `pred_use_in_order`（默认关）：

1. **阈值保守**：只有预测值 < 0.15（几乎肯定排不完）才剪；
2. **延迟而非丢弃**：被剪的候选进 `deferred`，其它候选全失败后**回来重试** ——
   最坏情况与不剪枝完全一致，绝不可能因为剪枝而报「无解」；
3. **只在前向检查之前剪**：容量/兼项的**确定性**判据永远优先，模型的判断不覆盖硬约束。

另外 `pred_use_in_order` 默认**关闭**：软排序信号（权重 0.3）在确定性 best-fit
已经够强时基本是噪声，开着它会在 HELL 档把未排从 9 抬到 10（**变差**）。

### 4.5 非对称损失：把 days / quality 变成可信的保守下界

依据 arXiv:2606.04860：MSE 训练的代价/价值网络会**系统性高估**，
破坏可采纳性。新增 `asymmetric_mse(pred, target, beta=3.0)` ——
**高估罚 3 倍、低估罚 1 倍**，接在 `days_head` 与 `quality_head` 上：

* `days_estimate` 偏高会被读成「这里还有空间」，把搜索引向更差的区域 → 罚高估；
* `quality_score` 偏高会被读成「这个方案不错」→ 同样罚高估。

于是两个头都变成**偏保守的下界式信号**。⚠️ 训练侧改动必须重训才生效（见 §6）。

### 4.6 规划层接进 Java：`PredictivePlanner` + 预演端点

Python 侧算法已**逐条移植**为 Java 实现，两边语义对齐（同一套前向检查、同一套代价、
同一套三动作计数），避免「线上与离线是两套只有名字相同的实现」。

| 组件 | 位置 | 作用 |
|---|---|---|
| `PredictivePlanner` | `com.sports.schedule.plan` | 纯静态入口，零依赖，**8 项单测**（兼项避让 / 诚实未排 / 让位链 / 确定性可复现 / 代价口径） |
| `PredictivePlannerService` | `com.sports.service.schedule` | 把规划器接到**真实赛会数据**（`Unit` × `Window` × 容量），返回方案 + 诊断 |
| `POST /api/schedule/plan` | `ScheduleController` | **预演端点**（只读不落库）：秒级回答「排不排得下、卡在哪」 |

设计要点：

* **`violations` 恒应为空**。它只承载「非法落位」（超容/兼项撞）。
  一旦非空即说明规划器产出了非法方案，属缺陷；「排不下」一律走 `unplaced`。
  把这两件事**分成两个字段**，是为了让「客观差多少」与「方案本身错」不可能被混淆。
* **只读预演**是刻意的：先让用户看得见可行性与诊断数字，再决定要不要花时间跑重档。
* ⚠️ 本项目的 `Window` **不带场地字段**（容量按「时段」给），所以容量键取
  `(时段, 单元自己的场地)`。这是与现有数据模型一致的**如实映射**，
  已在代码注释里写明；将来 `Window` 增加场地维度只需改一处。
* 前端已接入：赛程页新增「规划预演」按钮 + 诊断弹窗，展示
  **节点扩展数 / 落位 / 回退 / 修复 / 重启 / 让位回滚 / 剪枝 / 剪后重试** 八个数字，
  以及排不下单元清单与方案明细表。

## 5. 检索与判断的共同教训

1. **「不确定即信息」**（Generative LNS）：模型最没把握的地方，正是结构歧义/高耦合所在，
   优先处理收益最大 —— 我们已把它用在 LNS 破坏集（MC Dropout 方差）。
2. **「高估的代价远大于低估」**：预测只要参与剪枝，就必须先做保守化与校准。
3. **「失败分支要进训练集」**：只模仿成功路径的模型，学不会什么时候该放弃。
4. **「先判适用性，再判实现」**：检索结果里能落到具体数据列/决策点的才做，
   其余写进文档即可 —— 否则就是拿摘要当成果。
5. **「预算用尽 ≠ 结论为否」**（本轮新增，代价最大的一条）：
   把「搜索到一半停下」当成「查过了，不行」，会让**整批标签变成假的**。
   凡是「截断」，都必须把「未知」独立于「否」表达出来。
6. **「省下的资源要用得出去，才算收益」**（本轮新增）：
   预测器单次尝试省 65~89% 扩展，但同预算下总节省只剩 0~56% ——
   因为省下的预算被花在更多次重启上，而**当前的重启算子并没能提升解质量**。
   所以「更省」本身不是目的，**「省下来的预算有没有更好的花法」才是**。

2. 但四个算子**统计上旗鼓相当（11.2%~12.8%）**，没有单一算子显著胜出

### 6.1 `Repair` 块连续性修复 ✅

代价函数里 `breaks`（同组跨天）一直是计了费的，但修复层只修容量与兼项 ——
**罚了但不治**。本轮补上 `_repair_blocks`，实测（6 seeds、五档、R=8）：

| | breaks | 代价 | 搬动 |
|---|---|---|---|
| 关闭块修复 | 19.8 | 302.7 | — |
| **开启块修复** | **17.3** | **300.2** | BLOCK 1.8 / LANE 0.5 / TEAM 0.2 |
| 降幅 | **−12.6%** | −0.8% | |

演化过程与两个关键发现：
- 只做**直接搬迁**时 breaks 只降 5.0% —— 因为搬迁要求**锚点天有空余容量**，
  而紧实例里锚点天往往是满的（其它天反而有余）；
- 加上**交换**（容量守恒，一步换两人位置，不需要任何空闲容量）后升到 9.2%；
- 修掉一个**判定口径 bug** 后升到 **12.6%**：原先用 `verify_slot_map` 判合法性，
  而它把「未排」也算作不可行 → **部分解上任何修复都被误判成非法**，算子一步都动不了。
  新增 `_is_legal`（只判容量/兼项/场地开放，**不判完整性**）。
  这与 §4 修掉的「`violations` 不该混入未排」是同一条道理：**合法性 ≠ 完整性**。
- 还修掉「只试多数天当锚点」的缺陷：单元数打平时会挑到搬不动的那天，
  改为**逐个天试锚点**。

⚠️ headroom 有限是**真实的**：HELL/REGULAR 档一次都没搬动过 ——
它们的容量确实腾不出空间（连交换也找不到合法且能降低断裂的组合）。
剩余断裂是**结构性**的，要靠「给某天多配容量」（用户决策），不是更好的算子
—— 本轮已把它做成可执行闭环，见 §6.5。

### 6.2 专家表征同质化度量 ✅（结论：没有同质化问题）

⚠️ 不能用 MoE **融合后**的表征去比：那是各专家的加权和，差异会被平均掉。

实测（当前 17 专家权重，3 seeds）：

| 档 | 使用率最低 | 路由熵 | 相似度均值 | 相似度最高 | 跨组（任务×能力） | 能力组内 |
|---|---|---|---|---|---|---|
| HELL | 0.0308 | 0.9861 | **0.0363** | 0.8120 | 0.0654 | 0.0599 |
| REGULAR | 0.0300 | 0.9861 | 0.0757 | 0.8375 | 0.0830 | 0.0730 |
| BLOCK | 0.0254 | 0.9767 | 0.0628 | 0.8413 | 0.0818 | 0.0612 |
| LANE | 0.0234 | 0.9689 | 0.0243 | 0.8142 | 0.0522 | 0.0489 |
| TEAM | 0.0300 | 0.9864 | 0.0921 | 0.8626 | 0.1144 | 0.0728 |

### 6.3 加权代价口径（替代「单纯未排数」）✅

**问题**：四档编排模式（rule / optimize / ai / 混合）在魔鬼档之外**全部持平**。
定位结果是**指标分辨率**而不是搜索不足：那些实例的未排数已经贴近下界
（1.0 / 1.33），四档落在同一个数上 —— 未排是个位数小整数，对这些实例没有区分力。

**做法**：新增单一权值来源 `sports_ai/metrics.py`（Java 侧同表在 `PlanCost`），
四档对比与「AI ≤ GA」的验收判定改用**加权代价**：

| 分量 | 含义 | 权重 |
|---|---|---|
| 未排 | 任何可行时段都放不下（硬失败） | 1000 |
| 兼项撞 | 同一运动员落进重叠时段（方案本身是错的） | 500 |
| 容量超占 | 同段同场地已排时长 > 容量（方案本身是错的） | 500 |
| 道次撞 | 同批（同项目+同年级）落进同一时段 | 50 |
| 碎块 | 同组跨天的处数 | 10 |
| 工期超限 | 占用天数超 `days_limit` 的天数（三态：x / 0 不限 / −1 尽快） | 20 |

⚠️ 两条口径纪律：① **「能不能排」远重于「排得好不好」**（前三个分量比碎块高一到
两个数量级）；② 超占按**分钟**计价，所以「1 个未排 > 任意非法量」**不成立** ——
这是刻意的：非法方案**不可交付**，而少排一个单元至少还能交付一个合法的部分方案
（`test_metrics.py` 专门有一条用例防止后人按直觉"修正"它）。

**实测（3 seeds、深度 128 权重、不含预测器）**——四档编排模式：

| 档 | greedy（≈L2） | GA一条龙（L3） | 模型直出 | **AI 混合** |
|---|---|---|---|---|
| HELL | 16033.3 | 10380.0 | 15366.7 | **10040.0** |
| REGULAR | 3366.7 | 1370.0 | 3366.7 | **1370.0** |
| BLOCK | 12523.3 | 7873.3 | 11526.7 | **7873.3** |
| LANE | 2540.0 | 1156.7 | 2873.3 | **1156.7** |
| TEAM | 2033.3 | 1366.7 | 1370.0 | **1366.7** |

三个结论：

1. **HELL 档的优势放大且可分解**：AI 10040 vs GA 10380（差 340 = 0.33 个未排 + 0.7 处碎块）。
   旧口径只看到「未排 10.0 vs 10.33」，几乎是噪声；换口径后 340 分是**跨档可比的量**。
2. 其余四档 GA 与 AI **仍然持平 —— 但这次是结构原因**：L4 的最终解取
   「搜索最优 ∪ 全部种子」，而 GA 就是它的种子之一 → L4 只可能 ≤ GA，
   触到同一局部最优时**必然相等**。要在这四档分出高下是**搜索能力**问题
   （得让 L4 真搜出 GA 搜不到的解），不是口径问题。**换口径已经完成了它的任务：
   在有差异的地方把差异放大，在没有差异的地方说清为什么没有。**
3. ⚠️ **工期分量当时是死项**：默认场景生成器把窗口天数设成**恰好等于** `days_limit`，
   于是实际占用天数永远 ≤ 上限 → 超限恒为 0。分量接好了，却一次都没触发
   （典型的「接线正确但从未通电」）。修法：给生成器加 `extra_days`（默认 0，
   保持既有数据分布与结论可比），评测加 `--extra-days N`。

**工期压力口径实测（`--extra-days 2`，3 seeds）**：窗口天数 +2 而 `days_limit` 不变，
「必须压掉那几天」才真正成立：

| 档 | greedy | GA | 模型直出 | **AI 混合** |
|---|---|---|---|---|
| HELL | 9090.0 | 5096.7 | 11420.0 | **4760.0** |
| REGULAR | 1733.3 | 736.7 | 1733.3 | **736.7** |
| BLOCK | 2930.0 | 1593.3 | 3260.0 | **1593.3** |
| LANE | 1893.3 | 796.7 | 1246.7 | **796.7** |
| TEAM | 1386.7 | 1386.7 | 1386.7 | **1386.7** |

* 工期分量五档全部真正触发（每档 工期 ≈ 27 ≈ 1.33 天 × 20 分/天）；
* AI ≤ GA 五档全 ✅；HELL 仍是最大战场（4760 vs 5096.7）；
* 顺带钉住一条：**模型直出（L4 裸模型）在压力档远比 GA 差**（HELL 11420 vs 5096.7）——
  再次印证「纯 ONNX 直出不如搜索」，L4 的价值在**混合链路**而不是裸模型。

### 6.4 规划层作为 `ArrangeStyle` 的第 5 款型 ✅

`ArrangeStyle` 新增 `PLAN("plan","规划层")`，与 `CLASS / SNAKE / SNAKE_SEEDED / AI`
并列，`/api/arrange/styles` 自动列出（**前端零改动**：款型目录是动态拉取的）。

* **与蛇形家族互斥**：蛇形有意放开「同组不同班」，规划层**强制**它 —— 硬约束不同，
  所以单开一个 `isPlan()` 判定，而不是塞进 `isSnake()`（塞在一起是「改一个款型顺手
  改坏另一个」的常见来源）。
* **算法**：贪心打底（与「班级均衡」同口径）+ **显式代价的局部搜索**（搬迁 + 交换），
  代价 = `3 × 组人数极差 + 2 × 同班相邻组配对数`。只接受代价严格下降且不破坏硬约束的移动。
* **结构保证**：它从与「班级均衡」**同一个贪心解**出发、只接受严格变好的移动，
  所以目标函数 ≤ 起点 —— 「规划层不得比班级均衡更差」是**不变量**而非期望值
  （`arrange_planMode_isLegalAndNoWorseThanClass` 钉住它）。
* 抽出 `assignLanes` 作为**公共下游**：分道只认「该班已用该道的次数」，
  与选哪款入组规则无关 —— 各款型各写一份分道，就会出现「同一份报名换款型后
  道次公平性不一样」这种说不清的问题。

⚠️ 一处被自己否掉的代价项：最初把**「空道次浪费」**写进代价。但组数是**推导出来的常量**
（`max(⌈总人数/道次⌉, 最大班人数)`），所有能排下的运动员都会被排下 →
「占用道次总数」在任何布局下都相等 → 该项**恒为常数**，看着在优化，其实什么都没优化。
换成「同班相邻组配对数」（同班两人连着两趟上场 = 连轴转）后才有意义 ——
而且它**只有交换才动得了**（人数守恒、极差不变），这正是「为什么必须有交换」的理由：
只做搬迁时这一项永远优化不到。

### 6.5 给某天多配容量（把结构性断裂变成用户决策）✅

§6.1 的结论是「剩余断裂是**结构性**的，不是算子不好」。本轮把它接成一条**可执行的闭环**：

1. **配置侧**：`dayConfigs[i].extraMinutes`（默认 0）→ `buildWindows` 把它加到
   **该天每个时段**的容量上。
   ⚠️ **不改时段的起止时间**：起止时间决定「现场几点到几点」，是要打印进秩序册的**事实**；
   额外容量表达的是「这天还留了余量」，两者语义不同 —— 混在一起会让导出的时间表与容量对不上。
2. **诊断侧**：新增 `PlanAdvice` —— 对每个跨天的组找出**锚点天**（成员最多的那天），
   算出「把其余天的成员并过去还缺多少分钟」，并按天汇总。
   ⚠️ 同一天多个组报缺口时取**最大**而不是求和：新增容量是**可以共用**的，
   求和会把结论说满，反而误导（它是「**至少**加这么多才有可能用上」的下界）。
3. **交互侧**：预演面板新增 `weightedCost` / `costBreakdown` / `groupBreaks` /
   `extraMinutesByDay`，并给出「**给第 X 天 +N 分钟**」的一键按钮 ——
   点一下把建议值填进日程配置（**不自动保存**：配置里还有时段/场地/项目顺序，
   静默落库会覆盖用户正在编辑的内容）。
4. **端到端单测**（`adviceIsActionableAndEffective`）：三兄弟同组、锚点天只差 60 分钟 →
   建议值就是 60；按建议把 60 加进该天两个时段后重排，**断裂 1 → 0**。
   一条用例同时证明「建议算得对」「断裂确实由容量造成」「建议是可执行的」。
